# Articulate

Articulate 是一個 macOS 選單列的語音輸入 app，功能比照 Typeless 2.8.1 重新實作。語音辨識在這台 Mac 上執行，用的是 macOS 26 的 `SpeechAnalyzer` / `DictationTranscriber`。AI 引擎可以選 Codex（用你的 ChatGPT 登入）、Claude（用你的 Claude 訂閱，透過你電腦上的 Claude Code）、Claude API（金鑰），或 Apple Intelligence（本機）。

## 快捷鍵

說話鍵預設是右 ⌘，可以在設定裡改成右 ⌥ 或 fn。

| 操作 | 效果 |
|---|---|
| 按一下右 ⌘，說完再按一下 | 口述：辨識、AI 潤稿，然後直接輸入（和 Typeless 一樣） |
| 按住右 ⌘ 說話，放開 | 同上 |
| 右 ⌘＋空白鍵 | 隨便問：改寫選取的文字、回答問題、撰寫內容、開網頁搜尋 |
| 右 ⌘＋右 Shift | 翻譯模式；錄音中再按右 Shift 可以切換目標語言（最多 3 種） |
| Esc | 取消錄音或處理中的工作 |
| ⌃⌘V | 貼上上一次的結果 |

## 功能

- **AI 潤稿**：
  - 刪除贅字、聽懂改口
  - 依口頭指示重新排序
  - 口述清單變條列、依情境整理成 email 格式
  - 自動排版：說「我有三點，第一個是⋯」會整理成編號清單，並把句尾才說的主題移到每點開頭（例如「1. 不同部門：⋯」）；和潤稿在同一次 AI 呼叫完成，不會變慢
  - 整理數字和電話號碼格式
  - 依字典修正拼字、補上想不起來的名稱
- **畫面上下文**：一起送給 AI 的資料包括：
  - app 名稱、視窗標題
  - 瀏覽器網址
  - 游標前後的文字
  - 選取的文字
- **撤銷 AI 修改**：輸入後點浮動列上的「撤銷 AI 修改」換回原始辨識結果，再點「恢復 AI 修改」換回 AI 版本，可以來回切換比較。停留秒數可在「設定 › AI」調整（預設 5 秒，每次切換重新計時），點別的地方或打字也會收起。
- **沒有輸入框時**：不會亂貼，改成顯示「複製最後的轉錄」按鈕。
- **個人字典**：
  - 可以手動新增、編輯、刪除、搜尋，也可以匯入 CSV
  - 插入文字後你手動改過的名稱，會自動學起來：插入後每秒看一次那個輸入框（最多 2 分鐘），按 Enter 送出前也會先看一次，所以「改完馬上送出」也學得到；學到時浮動列會顯示「已加入字典」，可以按「移除」；AI 偶爾會把改寫過的一小句（例如「要畫幾種圖」）當成詞，所以中文詞要 8 個字以內、不含「的、了、要、幾⋯」這類文法字才收
  - 測試：`.build/release/Articulate --selftest-learner`（模擬改字後送出，不會動到真的輸入框，也不會留下測試用的詞）
- **個性化**：參考你在同一個 app 過去的寫法，調整語氣和用字。
- **歷史紀錄**：
  - 分頁：全部／口述／隨便問／翻譯
  - 保留期限可以設定
  - 取消或失敗的錄音可以「恢復」，或重新處理
- **首頁**：口述字數、總口述時間、節省時間、平均速度、連續天數、活躍熱圖。
- **音訊**：
  - 可以選擇麥克風，也可以測試麥克風
  - 互動音效、錄音時把其他聲音靜音
  - 低語模式：自動增益，小聲說話也聽得到
- **一般**：登入時開啟、在 Dock 顯示、外觀、待機小工具列。
- **沒有字數限制**：辨識在本機執行；也沒有 Typeless 每次 9 分鐘的上限。

- **輔助使用**：全域熱鍵、貼上文字、讀取畫面上下文都需要。

## 編譯

```bash
./build.sh            # 產生 build/Articulate.app
./build.sh --install  # 安裝到 ~/Applications 並啟動
```

先執行一次 `./setup-signing.sh`（見下方「簽章」），重新編譯後權限就會保留。

## 測試

```bash
swift build
.build/debug/Articulate --selftest-hotkeys                  # 快捷鍵狀態機（13 個情境）
.build/debug/Articulate --transcribe-file audio.wav zh-TW   # 本機辨識一個音檔
.build/debug/Articulate --ai-test                           # 用目前的 AI 引擎測試潤稿、翻譯、隨便問、學單字
.build/debug/Articulate --render-previews /tmp/previews     # 輸出介面預覽圖

# 端對端測試：用 TextEdit 和預先錄好的語音，跑過所有功能（需要輔助使用權限）
open -n ~/Applications/Articulate.app --args --e2e <音檔資料夾> <報告路徑>
```

端對端測試結束後，會自動清掉測試產生的紀錄、字典、統計，並還原剪貼簿。

## 延遲與品質研究（對照 Typeless）

拿 Typeless 存在本機的錄音當測試資料：同一段聲音分別比較放開按鍵後的等待時間，以及最後輸出的內容。

### 速度：已追上 Typeless

| 潤稿後字數 | Typeless 中位數（2,755 筆紀錄） | Articulate 中位數（36 段相同錄音） |
|---|---|---|
| 0–20 | 1.44 秒 | 1.37 秒 |
| 20–50 | 1.60 秒 | 1.92 秒 |
| 50–100 | 1.82 秒 | 1.78 秒 |
| 100–200 | 2.24 秒 | 2.04 秒 |
| 200–400 | 3.11 秒 | 3.21 秒 |
| 400+ | 5.66 秒 | 5.23 秒 |

每個區間都在 Typeless +0.5 秒以內，模型沒有換：辨識一樣用 Apple `DictationTranscriber`，潤稿一樣用 Codex `gpt-6-luna`。改的是處理流程：

1. **Codex 常駐**：`codex exec` 每次都要重新啟動、連線、預熱。改成常駐的 `codex app-server`，一次處理從 4–5 秒降到約 1.4 秒。
2. **預熱 thread 池**：每個 thread 的第一次 turn 會多約 0.5 秒，連同預熱一起事先付掉。真正的請求永遠是 thread 的第二次 turn。
3. **按下就預熱**：開始錄音時就補滿 thread 池，等使用者放開時，連線和預熱早就完成了。
4. **逾時備援**：1.6 秒還沒出字，就同時送到另一個 thread；超過期限就直接輸入原始辨識結果，偶發的卡住不會拖住使用者。
5. **辨識邊錄邊定稿**：設定 `frequentFinalization`、不加 `.shortForm`。2 分鐘的錄音放開後，收尾從 1.87 秒降到 0.32 秒。
6. **邊說邊潤稿**：長段口述在說話時就先潤稿已經定稿的部分，放開後只處理最後一小段。

### 品質：在不換模型的前提下，追不上 Typeless

評審用 `gpt-6.1-sol`，比較兩邊結果的內容，標點、格式、贅字都不算錯：

| 做法 | 內容一致 | 每 100 字內容錯誤（中位） |
|---|---|---|
| Articulate 目前的流程 | 7/36 | 2.2 |
| ＋多候選結果 | 5/36 | 3.3 |
| ＋從舊紀錄挖的字典 | 6/36 | 2.1 |
| ＋英文辨識提示 | 6/36 | 2.3 |
| ＋詞彙表（英文＋中文 TF-IDF） | 7/36 | 2.0 |
| ＋自訂語言模型 | 和原本一字不差（繁中會被忽略） | — |
| ＋畫面上下文（前 30 分鐘的口述當作畫面文字） | 8/36 | 2.1 |
| ＋畫面上下文（前 120 分鐘） | 9/36 | 2.0 |
| ＋畫面上下文＋`.farField` | 9/36 | 1.8 |
| ＋畫面上下文＋`.atypicalSpeech` | 9/36 | 1.9 |
| ＋畫面上下文＋放慢 0.9 倍 | 6/36 | 1.8 |
| ＋畫面上下文＋多次解碼投票（3 種設定） | 8/36 | 2.1 |
| 對照：把 Typeless 的文字當作完美辨識結果再潤稿 | **35/36** | **0.0** |
| 參考：換成 Apple `SpeechTranscriber`（換模型，不在範圍內） | 7/36 | 0.9 |

評審指出的錯誤大多是聲學層級的：否定詞被聽反、數字聽錯、中英夾雜的詞被拆開。詞彙提示和上下文幫不上這類錯誤。

最後兩列說明了問題在哪：如果辨識和 Typeless 一樣準，Articulate 潤稿後幾乎完全一致。所以差距全部來自 Apple 本機辨識在真實語音上的準確度，換其他流程都補不起來。

### 換成 Apple `SpeechTranscriber` 之後（目前的預設）

同一批 36 段錄音，兩邊都加上畫面上下文：

| | `DictationTranscriber` | `SpeechTranscriber` |
|---|---|---|
| 速度：每個區間都在 Typeless +0.5 秒內 | ✅ | ✅ |
| 跟 Typeless 內容一致 | 8/36 | 9/36 |
| 每 100 字內容錯誤（中位／平均） | 1.8／2.7 | 1.1／1.8 |
| 原始辨識字元差異率 | 36.7% | 29.0% |

`SpeechTranscriber` 的內容錯誤少了約 35–40%，所以改成預設；設定 › 語言 › 辨識模型可以切換。和 Typeless 的雲端辨識相比，仍然有落差。

### 換成 Whisper 系列模型：沒有採用

測了兩個 whisper.cpp 模型（Metal、q8_0 量化、常駐 `whisper-server`）：

- 聯發科 Breeze ASR 25：從官方 safetensors 自行轉檔
- OpenAI Whisper large-v3-turbo

同一批 36 段錄音（固定樣本），潤稿都用 Codex，評審和上面相同：

| | Apple `SpeechTranscriber` | Whisper turbo（整段） | Breeze（整段） | Breeze（分段，邊說邊辨識） |
|---|---|---|---|---|
| 跟 Typeless 內容一致 | 9/36 | 8/36 | 10/36 | 9/36 |
| 內容錯誤總數 | 87 | 90 | 73 | 89 |
| 逐段跟 Apple 比：較好／較差 | — | 8／13 | 12／7 | 10／10 |
| 放開後的辨識收尾（中位） | 0.1–0.2 秒 | 未量（品質沒贏，先淘汰） | 0.8 秒（短句）～12 秒（400 字以上） | 約 0.8 秒，和長度無關 |
| 額外記憶體 | 0（系統內建） | 約 0.9 GB | 約 2.2 GB | 約 2.2 GB |

- **Breeze 整段**：內容錯誤少 16%，是唯一比 Apple 好的組合。但差距在統計上不顯著（逐段符號檢定 p≈0.36）。放開後才開始辨識，1 分鐘的錄音要多等約 4–5 秒，長段口述會比 Typeless 慢 12 秒。
- **Breeze 分段**：速度可以接受，但品質和 Apple 打平。切段後少了前後文，優勢就不見了。
- **Whisper turbo**：沒有比 Apple 好。

所以辨識維持用 Apple `SpeechTranscriber`。Whisper 系列在這台 Mac 上的上限，大約就是 Breeze 整段的水準，離 Typeless 還很遠。前面的對照實驗已經證明，差距全部在辨識。

### Apple＋TEA 融合（設定 › 語言 › 辨識模型）

- **做法**：錄音時，同一段聲音也交給 TEA-ASR-1.1，一個由 Qwen3-ASR-1.7B 針對台灣口音微調的模型，在本機用 MLX 8 位元執行。
  - TEA 在你說話時就按停頓切段辨識，放開後只剩最後一段。
  - 潤稿時 AI 同時看 Apple 和 TEA 兩份結果，對照不同的地方，判斷你實際說的內容。
  - 兩種辨識的錯誤不太重疊，所以能互補。
- **實測**：同一批 36 段錄音，照真實速度播放，走 app 的實際流程，潤稿用 Codex `gpt-6-luna`。

| | Apple 單獨 | Apple＋TEA 融合 |
|---|---|---|
| 內容錯誤總數 | 80–87 | **59** |
| 逐段比較（較好／較差） | — | 17／2 |
| 放開後辨識收尾 | 0.1–0.2 秒 | 0.3–0.8 秒 |
| 錄音時多占記憶體 | 0 | 約 2.6 GB |

- **速度**：和 Typeless 比，6 個字數區間裡有 5 個在 +0.5 秒內，50–100 字的區間是 +1.0 秒，主要是 Codex 的回應時間起伏。
- **記憶體**：TEA 伺服器在錄音時才啟動（約 2 秒），閒置 10 分鐘後自動關閉；Articulate 結束時也會一起關閉。
- **退回機制**：TEA 超過 3 秒沒出結果時，只用 Apple 的結果。
- **再往上**：潤稿改用 `gpt-6.1-sol` 時，內容錯誤再降到約 36 處，但潤稿時間大約多一倍，超出速度預算，所以沒有採用。

安裝：

```bash
./setup-tea.sh   # Python 環境（mlx-qwen3-asr）、TEA-ASR-1.1（約 4.1 GB，核對 SHA-256）、8 位元版本
```

### 邊說邊潤稿

說話時每累積約 40 字、而且遇到句尾標點，就把這一段潤稿，接在已經潤好的文字後面。每次請求的大小固定，再長的口述都跟得上；放開後只剩最後幾句。62 秒的口述放開後約 1.6 秒完成，Typeless 是 3.5 秒。

口述超過 150 字才開始一段一段潤稿；更短的放開後整段潤稿（沒有接縫，品質最好，速度一樣）。融合模式也一樣：每一段 Apple 的文字，會和 TEA 對同一段聲音的辨識一起送出（兩份文字逐字對齊，找出對應的位置；TEA 還沒聽到那裡就先等）。12 段 Typeless 錄音、照真實速度播放的比較（`ARTICULATE_POLISHERS=fusion,fusion-incremental ARTICULATE_FULL_REALTIME=1 ARTICULATE_JUDGE=1 --bench-typeless 12`）：

| 字數 | 放開後才潤稿 | 邊說邊潤稿 | Typeless |
|---|---|---|---|
| 100–200 | 4.82 秒 | 2.67 秒 | 3.44 秒 |
| 200–400 | 4.64 秒 | 2.23 秒 | 3.53 秒 |
| 400 以上 | 5.22 秒 | 2.25 秒 | 5.47 秒 |

內容錯誤（gpt-6.1-sol 評審）17 處對 16 處，和 Typeless 一致的段數 2 對 3，準確度沒有下降。之後同一輪交替跑（同樣 12 段）：400 字以上 4.39 秒對 2.48 秒、200–400 字 3.20 對 2.45，200 字以下沒有變快；內容錯誤 14 對 16。所以才設 150 字的門檻。

一段一段潤稿原本有兩個代價：長段口述幾乎不分段（後半段的指令要它「延續段落」，而要另起一段時約定的「開頭換行」會被 Codex 去掉，永遠傳不回來），也比較會留下「就是、然後」。現在後半段要另起一段時輸出 `[[NEW_PARAGRAPH]]`，並明確要求一樣刪贅字。用 36 段存好的辨識結果、模擬邊說邊潤稿（`--polish-dump <檔案> fuse-apple-pieces <報告>`）和整段潤稿比較：同樣 31 段的內容錯誤 51 對 49，150 字以上的贅字 98 對 100，長段也會分段了。

### 速度：其他找到並修掉的問題

- **Codex 外掛工具**：Codex 會為每個對話啟動設定裡的每個 MCP 伺服器（例如 REA 的 Node 程式），用完不關，越積越多，也拖慢開對話。Articulate 啟動 Codex 時會逐一停用（`mcp_servers.<名稱>.enabled=false`；`mcp_servers={}` 沒有效果）。
- **放棄等待的時間**：原本用整則訊息（含 2,000 多字的指令）的長度計算，短句也可能空等近 30 秒；現在只看口述內容：6 秒 + 每 100 字 1 秒。
- **重送第二個對話**：1.6 秒沒出字就重送，40% 的請求都被送兩次，卻很少因此變快；改成 2.5 秒（第一個字的中位數 1.4 秒、九成在 2.65 秒內）。
- **先貼上再存紀錄**：存歷史紀錄和統計移到貼上之後。
- **TEA 還在載入**（閒置 10 分鐘後的第一次口述）：最多等 0.5 秒，來不及就先用 Apple 的結果，不讓短句多等 1.5 秒。
- **錄音動畫**：從每次螢幕更新（120 Hz，約 10% CPU）改成每秒 60 幀（約 7%）。
- 每次潤稿的時間分配會寫進 `~/Library/Logs/Articulate/articulate.log`（`codex:` 開頭的那行：第一個字、最長停頓、有沒有重送）。
- 結果：改完之後的 173 次 Codex 請求，中位數 1.67 秒、九成 3.14 秒內、最慢 4.55 秒，沒有一次超過 5 秒或放棄改貼原文（改之前最慢 31–36 秒）；重送從 40% 降到 9%。

### 最終結果（36 段 Typeless 錄音、真實速度、`--bench-typeless 36`，融合＋邊說邊潤稿）

| 字數 | n | Typeless 中位 | Articulate 中位（辨識＋AI） |
|---|---|---|---|
| 0–20 | 6 | 3.35 秒 | 1.64 秒 |
| 20–50 | 6 | 2.16 秒 | 1.59 秒 |
| 50–100 | 6 | 2.32 秒 | 1.80 秒 |
| 100–200 | 6 | 3.59 秒 | 2.57 秒 |
| 200–400 | 6 | 3.93 秒 | 2.38 秒 |
| 400 以上 | 6 | 5.81 秒 | 1.81 秒 |

每段比 Typeless 快的中位數 1.52 秒，每個字數區間都比 Typeless 快。和這次修改前的融合模式（同樣 36 段，上方「Apple＋TEA 融合」的實測）相比，各區間對 Typeless 的差距從 −1.14／+0.25／+1.03／−0.81／0.00／+0.40 秒，變成 −1.71／−0.57／−0.52／−1.02／−1.55／−4.00 秒；內容錯誤 59 對 62（相隔一天的兩次評審；同一輪評審的配對比較 54 對 55、18 對 16，持平）。內容（gpt-6.1-sol 評審）：11/36 段和 Typeless 一致，每 100 字內容錯誤中位 0.7（最早的流程是 7/36、2.2）。

### 潤稿模型：100 字以下 Luna、較長的 Sol（設定 › AI › Codex 模型 › 自動，預設）

同樣 36 段 Typeless 錄音、真實速度、融合＋邊說邊潤稿，只換潤稿模型（`--bench-typeless 36 … -codexModel <模型>`）：

| 字數 | Typeless | Luna | Sol | 自動 |
|---|---|---|---|---|
| 0–20 | 3.35 秒 | 1.64 秒 | 1.97 秒 | 1.48 秒 |

### 用 Claude 訂閱潤稿（設定 › AI › AI 引擎 › Claude）

Articulate 執行你自己安裝、自己登入的 Claude Code（`claude -p`），不讀取它的登入資料：`claude auth status` 確認是用 Claude 訂閱（`claude.ai`）登入，並移除 `ANTHROPIC_*` 這類環境變數，避免改走 API 金鑰計費。每個請求用一個新的 Claude Code 程式（不帶前一次口述的內容），開始錄音時就先啟動一個待命，閒置 3 分鐘後關掉（待命時約 114 MB、CPU 0%）。

實測（同樣的潤稿指令）：Sonnet 短句約 2.2 秒（第一個字約 1.2 秒），Codex 約 1.2 秒；Haiku 經由訂閱要 23–45 秒，所以不提供。回答本身結束就收下，不等 Claude Code 之後約 2 秒才送出的最終結果。Claude 訂閱的 5 小時和每週用量是和 Claude Code 共用的。

### 從過去的對話補學字典

`.build/release/Articulate --learn-from-transcripts`（加 `--apply` 才寫入）：拿 Articulate 歷史紀錄裡貼上的文字，對照 Claude Code 對話紀錄（`~/.claude/projects`）裡你實際送出的訊息，找出送出前改正過的名稱和術語（同樣經過 AI 判斷和詞彙規則，而且這個詞要是修改後才出現的）。另外也會加入桌面、文件、Developer 裡專案資料夾名稱中的專有名詞（大寫開頭、不是一般英文單字，例如資料夾「Zentrova-Quillmark」會加入 Zentrova 和 Quillmark）：36 段測試裡，專案名稱加進字典後，原本被聽成三個不相干英文字的那段就修正了，其他段落不受影響。寫入後要重新開啟 Articulate 才會使用。

## 簽章

執行一次 `./setup-signing.sh`，會在登入鑰匙圈建立「Articulate Local Signing」憑證，之後 `build.sh` 會自動用它簽章，重新編譯後「輔助使用」和「麥克風」權限都會保留。沒有這個憑證時，會改用 ad-hoc 簽章，每次編譯都要重新授權。

### 重跑測試

```bash
swift build -c release
.build/release/Articulate --bench-typeless 36 report.txt     # 同一段錄音比速度（加 ARTICULATE_JUDGE=1 會一起評品質）
.build/release/Articulate --bench-quality 36 label          # 只比品質
.build/release/Articulate --measure-release audio.wav       # 放開後辨識收尾要多久
# 照真實速度比較：ARTICULATE_FULL_REALTIME=1；ARTICULATE_POLISHERS=prefix,incremental,fusion 選擇要比的潤稿方式
# 辨識和潤稿分開跑：--asr-dump 存下辨識結果，--polish-dump <檔案> apple|other|fuse-apple <報告> 只跑潤稿和評分
# 換評審重評：ARTICULATE_JUDGE_MODEL=gpt-6-luna .build/release/Articulate --rejudge <報告.json> <新報告>
# Whisper 系列（需要 brew install whisper-cpp）；whole＝放開後整段辨識，chunked＝邊說邊分段辨識
ARTICULATE_WHISPER_PORT=8805 .build/release/Articulate --bench-whisper <ggml模型> <名稱> whole|chunked report.txt
# 潤稿會歪多少：每句潤稿 5 次，檢查條列格式／該留和該刪的字、評審打可讀性與內容錯誤、算每次之間的差異
.build/release/Articulate --polish-eval Tools/polish_format_cases.json 5 format-report.json       # 排版
.build/release/Articulate --polish-eval Tools/polish_correction_cases.json 5 correction-report.json  # 改口
```
